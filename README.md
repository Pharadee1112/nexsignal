# NexSignal: Prototype

เมื่อเกิดเหตุการณ์ภายนอก (น้ำท่วม พายุ ท่าเรือปิด) ระบบช่วยฝ่ายจัดซื้อรู้เร็วว่า**วัตถุดิบตัวไหน จะขาดเมื่อไหร่ เท่าไหร่**

> **ข้อมูลทั้งหมดเป็นข้อมูลจำลอง** ชื่อซัพพลายเออร์ สต็อก และคำตอบ สร้างขึ้นเอง ไม่ใช่ข้อมูลของ CPF

## วิธีรัน

```
python nexsignal.py          # demo + วัดผลตัวอ่านแบบกฎ (ไม่ใช้ AI)
```

วัดผลตัวอ่านแบบ AI ด้วย (ต้องมี API key ของ Anthropic)

```
pip install anthropic
set ANTHROPIC_API_KEY=sk-ant-...      (Windows cmd)
python nexsignal.py llm
```

## ไฟล์

| ไฟล์ | คืออะไร |
|---|---|
| `nexsignal.py` | โค้ดทั้งหมด |
| `data/suppliers.json` | ซัพพลายเออร์จำลอง 8 ราย: วัตถุดิบ ประเทศ พิกัด ท่าเรือ สต็อกพอใช้กี่วัน ของจะมาในกี่วัน |
| `data/events.json` | เหตุการณ์จำลอง 4 แบบ: น้ำท่วม พายุ ภัยแล้ง ท่าเรือประท้วง (รูปแบบคล้ายข้อมูลจาก GDACS) |
| `data/replies.json` | คำตอบจากซัพพลายเออร์ 40 ข้อความ 5 ภาษา (อังกฤษ ไทย โปรตุเกส สเปน เวียดนาม) พร้อม**เฉลย** |

## ระบบทำงานยังไง

| ขั้น | ฟังก์ชัน | ทำอะไร | ใช้ AI ไหม |
|---|---|---|---|
| 1 | (ข้อมูลเข้า) | รับเหตุการณ์ | ไม่ (ใช้ GDACS / GDELT ที่มีอยู่) |
| 2 | `affected()` | หาซัพพลายเออร์ที่อยู่ในรัศมี หรือใช้ท่าเรือเดียวกัน | ไม่ |
| 3 | `read_rules()` / `read_llm()` | อ่านคำตอบซัพพลายเออร์ แปลงเป็น `status`, `delay_days`, `deliverable_pct` | **`read_llm` ใช้ AI** |
| 4 | `impact()` | สต็อกเหลือเผื่อกี่วัน ขาดกี่ตัน ระดับความเสี่ยง | ไม่ (ลบเลข) |
| 5 | `options()` | หาซัพพลายเออร์วัตถุดิบเดียวกันที่ไม่โดนผลกระทบ | ไม่ |
| 6 | คน | ฝ่ายจัดซื้อตัดสินใจ | ไม่ |

**สูตรขั้น 4**
```
buffer_days = stock_days - (eta_days + delay_days)
short_tons  = order_tons x (100 - deliverable_pct) / 100
```

| ระดับ | เงื่อนไข |
|---|---|
| CRITICAL | buffer < 0 (สต็อกหมดก่อนของมา) |
| HIGH | buffer 0 ถึง 2 วัน หรือขาดตั้งแต่ 30% |
| MEDIUM | buffer 3 ถึง 4 วัน หรือขาดเล็กน้อย |
| LOW | อย่างอื่น |
| CHECK | ซัพพลายเออร์ยังไม่รู้ หรือไม่ได้บอกตัวเลข ต้องให้คนตามต่อ (ไม่คำนวณจากการเดา) |

**ตัวอย่างจาก demo:** น้ำท่วมท่าเรือ Santos กระทบ Supplier A (กากถั่วเหลือง) ซัพพลายเออร์ตอบว่าช้า 5 วัน ส่งได้ 60% สต็อกพอ 12 วัน ของเดิมมาใน 7 วัน
`buffer = 12 - (7 + 5) = 0 วัน` และขาด `5,000 x 40% = 2,000 ตัน` ระดับ **HIGH** ทางเลือก: Supplier B (อาร์เจนตินา)

## ผลวัด: ตัวอ่านแบบกฎ (ไม่ใช้ AI)

| ตัววัด | ผล |
|---|---|
| status ถูก | 39/40 (98%) |
| delay_days ถูก | 34/40 (85%) |
| deliverable_pct ถูก | 36/40 (90%) |
| ถูกครบทั้ง 3 ช่อง | 30/40 (75%) |
| ระดับความเสี่ยงถูก | 32/40 (80%) |
| **พลาดแบบอันตราย** (ความเสี่ยงจริงสูง แต่ระบบบอกว่าไม่เป็นไร) | **6/40** |

**ตัวอ่านแบบกฎพลาดตรงไหน:** คำที่ไม่ใช่ตัวเลข ("a week", "two weeks", "half", "ครึ่งเดียว", "หนึ่งสัปดาห์") และตัวเลขที่ไม่ได้หมายถึงสิ่งที่ส่งได้ ("lost 30%") พอหาตัวเลขไม่เจอ ก็ใส่ค่าเริ่มต้นว่า "ไม่ช้า ส่งได้ครบ" ทำให้**ประเมินความเสี่ยงต่ำเกินจริง** ซึ่งอันตรายที่สุด

**ข้อจำกัดของผลนี้:** คำสำคัญในกฎถูกเขียนโดยคนที่เห็นข้อความทดสอบแล้ว ผล 75% จึง**ดีเกินจริง** ถ้าเจอข้อความที่ไม่เคยเห็น ผลน่าจะแย่กว่านี้

## ผลวัด: ตัวอ่านแบบ AI

**ยังไม่ได้วัด** เพราะต้องใช้ API key โค้ดส่วนนี้ทดสอบแล้วว่าเชื่อมต่อและคำนวณต่อได้ถูก (ด้วยตัวจำลองที่ส่งเฉลยกลับมา) แต่ยังไม่ได้รันกับ LLM จริง

ตัวชี้วัดที่ต้องดูเมื่อรันจริง
1. **พลาดแบบอันตราย** ต้องน้อยกว่าตัวอ่านแบบกฎ (6/40)
2. ถูกครบทั้ง 3 ช่อง ต้องมากกว่า 75%
3. ข้อความที่ยังไม่รู้ผลกระทบ ต้องตอบ `Unknown` ไม่เดาตัวเลขเอง

## เราไม่ได้สร้างตัวเฝ้าระวังภัยพิบัติ/สงครามใหม่ เราใช้ของที่มีอยู่แล้ว

จุดสำคัญที่ต้องพูดให้ชัดตอนพรีเซน: **ขั้นที่ 1 (เฝ้าระวังว่าเกิดอะไรที่ไหน) ไม่ใช่สิ่งที่เราต้องสร้างเอง** มีองค์กรใหญ่ทำไว้แล้วและให้ใช้ฟรี เราแค่ **ต่อยอด** จากข้อมูลนั้น ไม่ได้แข่งสร้างระบบเฝ้าระวังโลกขึ้นมาใหม่

| เครื่องมือที่มีอยู่แล้ว | ใครทำ | ตรวจอะไร | ใช้ยังไง |
|---|---|---|---|
| **GDACS** (Global Disaster Alert and Coordination System) | UN + EU ร่วมกันทำ | น้ำท่วม พายุ แผ่นดินไหว ภัยแล้ง ไฟป่า ทั่วโลก พร้อมพิกัด/ระดับความรุนแรง | ดึงมาเป็น `data/events.json` ของเรา (ใน prototype นี้เป็นข้อมูลจำลองรูปแบบเดียวกัน ของจริงดึงจาก GDACS API ได้ฟรี) |
| **GDELT** | โครงการวิจัยที่ติดตามข่าวทั่วโลก | ข่าวสงคราม การประท้วง การปิดท่าเรือ ความไม่สงบ อัปเดตทุก 15 นาที แปลให้แล้วกว่า 65 ภาษา | ใช้เป็นสัญญาณเตือนสำหรับเหตุการณ์ที่ GDACS ไม่ครอบคลุม (เช่น สงคราม การประท้วง) |

**เราต่อยอดตรงไหน (ส่วนที่เราสร้างเอง และเป็น AI จริง ๆ):**

| ขั้น | GDACS/GDELT ทำให้ | NexSignal ทำต่อ (ของเราเอง) |
|---|---|---|
| 1. รู้ว่าเกิดอะไร ที่ไหน | ✅ ทำให้แล้ว ไม่ต้องสร้างใหม่ | — |
| 2. รู้ว่า **ซัพพลายเออร์ CPF** คนไหนอยู่ในพื้นที่นั้น | ❌ GDACS/GDELT ไม่รู้จักซัพพลายเออร์ของ CPF | ✅ `affected()` จับคู่พิกัด/ท่าเรือเหตุการณ์ กับพิกัด/ท่าเรือซัพพลายเออร์ในฐานข้อมูลของเรา |
| 3. รู้ว่าซัพพลายเออร์คนนั้น **จะส่งได้จริงไหม ช้าแค่ไหน** | ❌ ไม่รู้ ต้องถามซัพพลายเออร์เอง | ✅ `read_rules()` / `read_llm()` อ่านคำตอบซัพพลายเออร์ (ข้อความภาษาอะไรก็ได้) แปลงเป็นตัวเลข |
| 4. รู้ว่ากระทบ CPF แค่ไหน (ขาดกี่วัน กี่ตัน) | ❌ ไม่รู้สต็อก/ออเดอร์ของ CPF | ✅ `impact()` เอาตัวเลขจากข้อ 3 มาคำนวณกับสต็อกคงเหลือจริงของ CPF |
| 5. บอกทางเลือกสำรอง | ❌ ไม่รู้ว่า CPF มีซัพพลายเออร์สำรองที่ไหน | ✅ `options()` ค้นในฐานข้อมูลซัพพลายเออร์ของ CPF เอง |

สรุปเป็นประโยคเดียวสำหรับพรีเซน: **"เรื่องภัยพิบัติ/สงครามเกิดที่ไหน มีคนทำไว้ให้แล้วและฟรี (GDACS, GDELT) เราไม่เสียเวลาสร้างใหม่ แต่สิ่งที่ไม่มีใครทำให้ คือการแปลงข่าวนั้นให้เป็น 'วัตถุดิบ CPF ตัวไหนจะขาด เมื่อไหร่ เท่าไหร่ และมีตัวเลือกอะไรบ้าง' ส่วนนี้คือ AI ของเราและเป็นของที่เราสร้างเอง"**

ข้อดีของการพูดแบบนี้ตอนพรีเซน: ตัดคำถามกรรมการที่ว่า "ทำไมไม่ใช้ของที่มีอยู่แล้ว" ไปเลย เพราะเราบอกตรง ๆ ว่าเราใช้มันอยู่แล้ว (ไม่ได้แข่ง ไม่ได้ไม่รู้ว่ามันมี) แต่สิ่งที่เราสร้างคือ "ชั้นสุดท้าย" ที่แปลงสัญญาณเตือนทั่วโลกให้เป็นสิ่งที่ฝ่ายจัดซื้อ CPF เอาไปใช้ตัดสินใจได้จริงในวันนั้น
